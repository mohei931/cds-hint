# 接入设计说明

> 面向"如何把本原型接进医院现有环境"的工程说明。这里是演示用方案，不含任何真实患者数据。

## 1. 分层架构

```
┌─────────────────────────────────────────────────────────┐
│  接入层                                                   │
│  ① Web 工作台（医生手动录入，本仓库 web/index.html）        │
│  ② HIS/EMR 接口（预问诊、门诊病历、急诊分诊单自动带入）       │
│  ③ 第三方系统回调（仅暴露 HTTP API）                        │
└──────────────────────────┬──────────────────────────────┘
                           │ 结构化 CaseIn
┌──────────────────────────▼──────────────────────────────┐
│  推理层  app/engine.py                                    │
│  情景路由 → 红旗征筛查 → 鉴别打分 → 检查/问诊建议生成        │
│  可解释：每项输出都带 evidence 与 score                    │
└──────────────────────────┬──────────────────────────────┘
                           │ Assessment
┌──────────────────────────▼──────────────────────────────┐
│  知识层  knowledge/presentations/*.json（每病种一个文件）    │
│  （建议院内改为版本化知识库 + 双人复核发布流程）             │
└─────────────────────────────────────────────────────────┘
                           │（可选）
┌──────────────────────────▼──────────────────────────────┐
│  解释层  app/llm.py（只复述结构化结果，禁止新增诊断/用药）    │
└─────────────────────────────────────────────────────────┘
```

**关键设计取舍**：诊断逻辑放在规则层而不是交给大模型。原因是可解释、可审计、可被临床专家逐条修改；LLM 只承担"把结构化结论说人话"的角色，即使挂掉也不影响主流程。

## 2. 三种接入方式

| 方式 | 适用 | 做法 | 注意 |
| --- | --- | --- | --- |
| 独立工作台 | 试点、教学、演示 | 部署本服务，医生手工录入主诉与体征 | 需明确"提示不入病历"的边界 |
| EMR 内嵌（推荐） | 门诊/急诊真实使用 | 从病历编辑器或分诊单取结构化字段，POST `/api/assess`，结果以侧栏卡片展示并回写"是否采纳" | 写回只在医师确认后；带 request_id 做幂等 |
| 批量离线评估 | 上线前验证 | 用历史脱敏数据批量调用引擎，统计漏诊召回与建议检查冗余度 | 必须脱敏，且不得用评估结果反推患者身份 |

## 3. 接口契约

### `POST /api/assess`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| complaint | string ≤500 | 建议 | 主诉自由文本 |
| symptoms | string[] | 否 | 症状/体征关键词，权重与自由文本一致 |
| history | string[] | 否 | 既往史、用药、手术史 |
| age | int 0–120 | 否 | 用于风险修饰（如年龄≥45 增加 ACS 权重） |
| sex | `male`/`female` | 否 | 同上 |
| vitals | object | 否 | `temp/hr/rr/sbp/dbp/sbp_diff/spo2`，参与红旗判定 |

响应关键字段：

| 字段 | 说明 |
| --- | --- |
| `matched_presentation` | 命中的临床情景；未命中返回 `status=no_match` |
| `red_flags[]` | 红旗征，含 `urgency`、`evidence`、`action`、`exams` |
| `differentials[]` | 鉴别提示，含 `score`、`match_level`、支持/反向/缺失线索、建议检查、`caveat` |
| `recommended_exams[]` | 按「优先完成 / 按需完善」分组的合并检查清单 |
| `next_questions[]` | 建议继续采集的信息 |
| `disclaimer` | 免责声明，前端必须展示，不可隐藏 |

**调用约定**：超时建议 3s（规则引擎通常 <50ms，LLM 解释层另计）；失败时前端必须降级为"暂不可用"，不得让医生以为"没有红旗征"。

## 4. 扩展知识库

新增一个情景，只需在 `knowledge/presentations/` 下新增一个 JSON 文件：

```json
{
  "id": "dizziness",
  "name": "头晕/眩晕",
  "entry_terms": [{"term": "头晕", "weight": 2}],
  "red_flags": [{ "label": "疑似后循环卒中", "urgency": "立即",
                  "terms": ["构音障碍", "吞咽困难", "共济失调"], "min_hits": 2,
                  "action": "启动卒中绿色通道", "exams": ["头颅MRI"] }],
  "differentials": [{ "id": "bppv", "name": "良性阵发性位置性眩晕",
                      "support": [{"term": "体位变动诱发", "weight": 1.5}],
                      "against": [{"term": "构音障碍", "weight": 1}],
                      "exams": ["Dix-Hallpike 试验"] }]
}
```

约定：`support` 写"支持该诊断的阳性线索"，`against` 写"指向其他诊断、应减分的线索"，`critical: true` 表示漏诊代价高的危重鉴别，`min_hits` 控制红旗规则的触发门槛。修改后跑 `python -m unittest discover -s tests` 回归。

## 5. 上线前必须补的能力

1. **否定与不确定识别**：当前子串匹配会把"无胸痛"识别为有胸痛，必须先加否定词典与句法窗口，否则不可用于真实文本。
2. **同义词归一**：建立院内术语表，映射到知识库标准词（ICD-11/SNOMED 可作参照）。
3. **知识库治理**：JSON Schema 校验 + 临床科室双人复核 + 版本号与生效时间，变更留痕。
4. **评测**：构造含明确结局的评测集，统计红旗召回率、鉴别 Top-3 命中率、建议检查冗余度、医师采纳率。
5. **审计日志**：输入、命中规则 ID、输出、医师采纳/驳回、耗时，全部落库并可按患者就诊号追溯（日志本身需加密与访问控制）。

## 6. 监管与伦理提示

- 若产品对诊断具有实质辅助作用，通常落入医疗器械软件监管范围，需按相应类别注册或备案；仅在院内科研使用也需通过伦理审查与数据使用审批。
- 不得把可识别患者信息发送给外部大模型服务；如使用外部模型，需先脱敏并确认服务方合规资质。
- 界面必须持续展示"提示非诊断"的声明，禁止默认勾选、禁止自动写入诊断字段。
